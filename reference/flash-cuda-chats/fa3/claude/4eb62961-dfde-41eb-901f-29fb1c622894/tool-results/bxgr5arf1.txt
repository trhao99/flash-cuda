Closing the perf gap in `kernels/fa3_hopper.cu` vs vLLM FA3 baseline on H200 (sm90). Started 2026-07-22.
Target slow scenarios (bench: `python -m bench.eval --set real` + hd256 fp8 configs from attntest).
Baseline geomean over the 12 targets was **0.735x**.

**Iteration is expensive: each `bench.eval` rebuild of the 210KB kernel is ~200s (ptxas over all template instantiations, unavoidable). Batch high-confidence changes; use 2 GPUs (`--gpu 0/1`) + copied .cu variants to test in parallel.** Profile the prebuilt `.so` in `.fa3_trials/<ns>/` with `FA3_NS=<ns> FA3_CFG=<cfg> ncu ... python -m bench.prof_real` (no rebuild).

Key FA3 mechanisms reverse-engineered (reference/vllm-flash-attention/hopper/):
- **Paged decode/prefill (page_size=1) uses cp.async, NOT TMA** (tile_size.h: paged_kv_non_TMA → kBlockN=128). FA3 hits 89% DRAM BW at the SAME 12.5% occupancy / num_splits=1 as us. The lever is CN=128 + a barrier-free page-pointer resolve (each thread loads 1 page_table entry, `__shfl` broadcasts across the 8 threads/row). Its num_splits heuristic returns 1 when batch*heads already fills the SMs.
- **fp8 hd256 uses RS-PV** (P kept in registers, MmaPV_is_RS=true), CN=128, IntraWGOverlap. Not a smem P round-trip.

Changes that WORKED (in fa3_hopper.cu working tree):
1. Decode deep CN 64→128 (`DCN_D` for hd128 in launch_decode_split): decode DRAM 41→53%, geomean of 7 decode cfgs way up. **CN halving the tile count (per-tile softmax/pipeline overhead) is the win, NOT more pipeline stages.**
2. Barrier-free COOP gather (prefill_kernel producer): replace 2-pass smem-prefetch + `bar.sync` with per-lane page LDG + `__shfl`. decode DRAM 53→57%, s16k 0.72→0.81. **MUST spread the page LDGs across all 128 lanes** — concentrating on col_th==0 + shfl was 2.6x SLOWER (reproduced the old "serialized 2x" warning). [[fa3-cuda-eval-harness]]
3. fp8 hd256 → RS-PV at CN=128/STAGES=2 (build_P_rs_fp8/pv_fp8_rs templated on CN; drop sP smem tile; gated `RS=(HD==256)`). [status: in progress]

4. fp8 hd256 decode CN 64→128 (launch_decode_split_fp8 FCN): 0.76→0.89x (mirrors bf16 decode CN win).
5. Persistent paged prefill: added a COOP-gather branch (`if constexpr(!USE_TMA)`) to prefill_persist_kernel + a paged persist launch branch, GATED to total_work<=12*num_sm (helps small-grid s2k/qwen +2-5%, neutral/regresses huge-grid s16k where per-tile HW scheduling is already optimal). Dense TMA persist path untouched.
7. **fp8 COOP coalesced gather (BIG win)**: the fp8 producer (prefill_fp8_kernel issue_load) was still using the NAIVE 1-thread-per-key gather (gather_row_k8_cp/gather_row_plain8_cp) = uncoalesced (32 rows-256B-apart/warp = 32 scattered sectors), pinning fp8 prefill at ~19k long_scoreboard. Replaced with the same coalesced COOP (TPR8=HD/16 lanes/key + __shfl page resolve), gated COOP8 (needs TPR8 power-of-2 dividing WG; hd96 keeps per-key fallback). hd256 fp8 prefill 0.841->0.917, decode 0.887->1.022. THIS was the fp8 lever, not just RS-PV.
8. **bf16 rescale-reschedule (FA3 schedule)**: our qk_rs_pv_g put rescale_o (64 ALU) BETWEEN the QK(i+1) and PV(i) wgmma issues, delaying PV and cutting QK||PV overlap (34% tensor vs FA3 56%). FA3 issues QK+PV back-to-back then rescales O AFTER PV. Added qk_pv_g (no rescale) + moved rescale_o_g to after wgmma_wait0 in both prefill_kernel and prefill_persist_kernel consumer loops; removed the epilogue pre-PV rescale. Online-softmax stays correct (O rescaled to running max at END of each step, ready for next step's PV). [measuring v10]
9. Async page-row ring (cp.async page entries into smem double-buffer, gather reads smem not LDG) — TRIED, REVERTED (s16k 0.73->0.475: per-tile pfull/pempty+fence overhead >> the LDG it hid on many-tile prefill). Diagnosis of page-LDG-on-critical-path was WRONG.

**BIG WIN (v14): COOP gather TPR=8, not 16.** Matching FA3's kGmemThreadsPerRow=8 (8 lanes/row, KIT=HD/64 chunks/lane = 128-byte/1-cache-line bursts) instead of 16 lanes/row (256-byte/2-line bursts) lifted bf16 PAGED prefill 0.69-0.73->0.77-0.84x AND decode long-ctx 0.82->0.91x. The 15.6-sectors/req "optimal coalescing" metric HID this: 256B spans 2 cache lines and the memory system is far more efficient with 128B single-line requests. LESSON: don't reason away access-granularity; TEST it. (prefill_kernel COOP + persist load_kv_coop both TPR=8 now; COOP gate changed to HD%64==0.)

bf16 PAGED PREFILL — earlier lever (v13): FA3 paged-prefill profile (device_kernel, ncu -k "device_kernel") is tensor 55.8% / SFU(xu) 29% at 1 CTA/SM; ours was 34.9% / 19.3% at the SAME occupancy. Cause: our PV emitted N SEPARATE wgmma groups (pv_box64 committed per 64-col box -> QK+PV = 3 groups for hd128), so wgmma_wait1 left only the LAST box in flight to overlap softmax. Fix: pv_boxes now wraps ALL boxes in ONE wgmma group (single fence + all pv_box64_body + single commit) -> the full PV overlaps softmax (FA3's 2-group QK/PV pipeline). Affects all bf16/fp16 prefill+decode. [measuring v13]

bf16 PAGED PREFILL residual (0.69-0.73) — earlier ruled out structural causes: coalescing optimal (15.6 sec/req), NO register-serialization (C7512 warning only on hd192, never hd128), occupancy matched FA3 (1 CTA/SM), rescale placement matched FA3, 4 page-LDG-hiding attempts all regressed. Dense bf16 prefill (TMA, near-free 1-thread producer) BEATS FA3 at 1.03x; paged uses cp.async (128-thread producer, 2048 loads/tile). Both FA3 and we use cp.async for page_size=1; FA3's is 1.45x more efficient => residual is CUTLASS instruction-scheduling quality on the cp.async paged mainloop at 1 CTA/SM, NOT a structural/algorithmic gap. Levers exhausted without a further win.

6. 1-tile page-row prefetch in the COOP gather — TRIED, REVERTED. Made decode/prefill ~1-2% WORSE: the page-LDG was already hidden by the STAGES pipeline; the prefetch only added register pressure. Confirms the prefill bottleneck is NOT the page LDG but deep mainloop scheduling (wgmma-wait + load latency unhidable at 1 CTA/SM), which CUTLASS's generated code overlaps better — a hand-tuning-vs-CUTLASS gap.
